# Module 0 Note

## 第一章：从全局视角理解本次作业

Module 0 是 MiniTorch 的地基。它还没有真正进入“自动微分”或“反向传播”的实现，但它在为后面的 Module 做准备：后面所有 Scalar、Tensor、神经网络层、优化器，最后都会建立在本模块的基本数学函数、参数管理和测试习惯之上。

可以把一个深度学习框架想象成一座房子。Module 0 做的不是搭屋顶，而是在铺地基：

- 数学算子是砖块，例如加法、乘法、取反、sigmoid、ReLU。
- 测试是水平尺，用来检查砖块是不是直的。
- 高阶函数是简单工具，用来把“一个数上的操作”推广到“一组数上的操作”。
- `Module` 和 `Parameter` 是将来搭神经网络时的结构框架，用来组织层和参数。
- 数据集和手工分类器让学生第一次看到：这些小函数最后会服务于分类任务。

### 1. 本模块到底要做什么

本模块主要完成五件事：

1. 实现基础数学函数。
2. 为这些函数写性质测试。
3. 实现 `map`、`zipWith`、`reduce` 这类函数式工具。
4. 实现一个能保存子模块和参数的 `Module` 系统。
5. 用手工设置的线性分类器可视化一个简单数据集。

这五件事看起来分散，其实都在回答同一个问题：一个深度学习框架最小需要什么？

答案是：它至少需要能做数学计算，能验证数学计算，能组织参数，还能把这些参数放进一个模型结构里。

### 2. 它在整个课程中的位置

后续 Module 会逐步加入：

- Module 1：Scalar 自动微分。
- Module 2：Tensor 自动微分。
- Module 3：更快的 Tensor 运算。
- Module 4：更真实的深度学习模型。

Module 0 不是最终系统，但它定义了最基础的语言。例如 Module 1 中的 `ScalarFunction` 会调用这里的 `operators`；Module 2 的 Tensor 后端也会继续复用这些数学函数。

如果 Module 0 的 `sigmoid`、`relu`、`log_back` 这些函数写错，后面的自动微分即使框架结构正确，也会算出错误梯度。

### 3. 为什么深度学习框架需要这些基础件

一个神经网络本质上是一串函数组合。比如一个非常小的模型可以写成：

```text
输入 x
先做线性组合 z = w * x + b
再做非线性变换 y = sigmoid(z)
```

这里面需要加法、乘法、sigmoid。训练时还需要知道输出对参数 `w` 和 `b` 的变化方向，这就会涉及导数和反向传播。

Module 0 还没有实现反向传播，但已经实现了一些“将来反向传播会用到的局部导数函数”，例如：

- `log_back`
- `inv_back`
- `relu_back`

它们的作用可以先这样理解：当后面系统知道某个函数输出端的梯度时，这些函数负责把梯度往输入端传回去。

### 4. 计算图、forward、backward 和本模块的关系

本模块不会真的构建计算图，但学习时需要提前知道这个概念，因为后面 Module 1 和 Module 2 会直接使用它。

计算图可以理解成一张“计算流程图”。每个圆点是一个值，每条边表示这个值是如何由前面的值计算出来的。例如：

```text
x ----\
      multiply ---- z ---- sigmoid ---- y
w ----/
```

在深度学习框架里：

- forward 指从输入一路算到输出。
- backward 指从输出的误差一路反推每个参数应该如何改变。
- 梯度表示“如果这个值稍微变大一点，最终结果会怎么变”。

为什么不手写每个参数的导数？因为真实神经网络有成千上万个参数，手写不现实，也容易错。框架需要把每一步基础运算都写正确，然后让系统自动组合它们的导数。

Module 0 做的正是“把每一步基础运算写正确”。

### 5. `Module` 和 `Parameter` 为什么存在

一个神经网络通常不是一堆散落的变量，而是有层次结构的：

```text
Network
  layer1
    weight
    bias
  layer2
    weight
    bias
```

`Module` 就是这种树状结构的容器。`Parameter` 是需要训练的值。后面优化器会问模型：“请把你所有参数都交出来。” 如果没有 `Module.parameters()` 和 `Module.named_parameters()`，优化器就不知道该更新哪些值。

这就是 Module 0 中参数树的意义：它为后面的训练循环做准备。

### 6. 完成本模块前需要理解的知识

学生不需要提前懂完整深度学习框架，但需要先理解这些基础：

- Python 函数：输入、输出、返回值。
- 浮点数：计算机里的小数有精度误差，所以测试不能总用严格相等。
- 简单导数直觉：导数描述“输出对输入变化有多敏感”。
- 列表和循环：后面高阶函数会把循环抽象成函数。
- 类和对象：`Module`、`Parameter` 都是对象。
- 树结构：一个模块可以包含子模块，子模块还可以继续包含参数。

### 2. Task 0.1：基础算子

需要写代码的文件：`Human/0_torch_basics/minitorch/operators.py`。

你要在这个文件里完成基础标量函数，包括：

- 局部反向函数：实现 log、inv、ReLU 对应的 backward helper，让后续自动微分模块能调用。

#### 知识点：标量原语与局部导数

这些函数是 MiniTorch 后续所有 Scalar 和 Tensor 运算的最小数学原语。前向函数只回答“输入怎样变成输出”；对应的 backward helper 则回答“已知输出方向传回来的梯度时，当前输入应收到多少局部贡献”。它们不负责遍历计算图，只描述单个数学操作附近的变化率。

#### 大概实现逻辑

先按函数签名逐一确认输入、输出和边界语义，再使用 Python 的基础算术或 `math` 运算完成单次标量计算。比较函数要把真假转换成作业约定的数值信号；非线性函数要特别检查大正数、大负数和定义域边界；backward helper 则把上游梯度与对应局部导数结合，并只返回当前输入位置的结果。完成后用少量手算样例检查数值方向，再交给性质测试覆盖更广输入。

#### 大概实现逻辑

- sigmoid 的输出范围和基本形状。
- 小于关系的传递性。

- 加法和乘法之间的分配关系。
- 列表级别的求和、逐元素相加、高阶函数组合是否一致。

- 忽略浮点误差，用严格相等比较所有小数。

### 4. Task 0.3：高阶函数

需要写代码的文件：`Human/0_torch_basics/minitorch/operators.py`。

你要在这个文件里完成两层内容：

1. 通用高阶函数：`map`、`zipWith`、`reduce`。
2. 由高阶函数组合出来的列表工具：`negList`、`addLists`、`sum`、`prod`。

这里的重点是让通用函数承担遍历责任，具体算子只作为参数传进去。不要为每个列表工具单独写一套循环逻辑；那样虽然可能过一两个例子，但会绕开本任务真正要练的抽象。

#### 先理解“高阶函数”

这里的 `map`、`zipWith`、`reduce` 都不是接收列表后立刻计算，而是先接收一个“如何计算”的函数，再返回一个真正处理列表的新函数。可以把调用过程分成两个阶段：

1. 配置阶段：把标量函数以及必要的初始值交给高阶函数，确定每一步要做什么。
2. 执行阶段：把列表交给配置完成的新函数，由它统一负责遍历和组织结果。

这种设计把“遍历列表”与“处理一个元素”分开了。高阶函数只关心遍历规则，传入的函数只关心单步计算规则。

#### `map` 的逻辑

`map` 表示“一对一变换”。它接收一个只处理单个元素的函数，返回的新函数再接收一个可迭代对象。执行时，每个输入元素都独立经过同一个函数，并按照原有顺序形成一个新的列表。

思考它时可以追踪下面的数据关系：

```text
A 类型的元素 -> 单元素函数 -> B 类型的元素
Iterable[A]   -> map 后的新函数 -> List[B]
```

因此，输入与输出的元素个数通常相同，但元素类型可以发生变化。实现时应考虑如何逐个取得元素、保存每次调用的返回值，以及如何避免修改原输入。

#### `zipWith` 的逻辑

`zipWith` 表示“按位置合并”。它接收一个需要两个参数的函数，返回的新函数再接收两个可迭代对象。执行时，第一个位置的两个元素组成一对，第二个位置的两个元素组成一对，以此类推；每一对都交给同一个二元函数，并把结果按顺序放进新列表。

它的数据关系是：

```text
(A 类型的元素, B 类型的元素) -> 二元函数 -> C 类型的元素
(Iterable[A], Iterable[B])    -> zipWith 后的新函数 -> List[C]
```

这里需要特别想清楚两个列表长度不同时遍历应在哪里停止。可以参考 Python 内置 `zip` 的配对规则理解预期行为，但仍需自己组织函数结构。

#### `reduce` 的逻辑

`reduce` 表示“逐步累积”。它先接收一个累积函数和一个初始值，返回的新函数再接收可迭代对象。与前两个函数不同，它不会为每个元素保留一个独立输出，而是维护一个不断更新的累积结果：初始结果来自 `start`，随后每读到一个元素，就把“当前累积结果”和“当前元素”一起交给累积函数，得到下一轮结果。遍历完成后只返回最终累积值。

可以把过程理解为状态的连续传递：

```text
初始值 -> 与第 1 个元素合并 -> 中间结果
中间结果 -> 与第 2 个元素合并 -> 新的中间结果
...
最后一个中间结果 -> 最终结果
```

初始值不仅决定第一步从哪里开始，也决定空列表应返回什么。因此，用加法折叠和用乘法折叠时，初始值需要符合各自运算的语义。

#### 本任务用到的 `typing` 组件

`typing` 中的这些名字用于描述函数之间的数据契约，帮助读者和类型检查工具理解代码；它们本身不会执行遍历或计算：

- `TypeVar("A")`、`TypeVar("B")`、`TypeVar("C")`：定义泛型类型变量。它们不是三个固定的 Python 类型，而是表示同一次调用中需要保持一致的类型关系。例如，`A` 表示输入元素类型，`B` 或 `C` 可以表示变换后的结果类型。
- `Callable[[参数类型], 返回类型]`：表示“可调用对象”。方括号内前一部分列出调用它时需要的参数类型，最后一部分表示返回类型。`Callable[[A], B]` 描述一个把 `A` 变成 `B` 的单参数函数；`Callable[[A, B], C]` 描述一个接收 `A`、`B` 并产生 `C` 的二元函数。
- `Iterable[A]`：表示可以逐个取出 `A` 类型元素的对象。它比 `List[A]` 范围更广，因此列表、元组和其他可迭代对象都可能作为输入。实现时不要依赖只有列表才有的操作。
- `List[B]`：表示最终返回的是一个列表，并且列表元素属于 `B` 类型。它描述的是输出容器，不代表输入也必须是列表。

阅读嵌套的 `Callable` 时，从外向内分两层看。例如，“接收一个元素函数，返回一个列表函数”意味着：外层调用负责接收计算规则，内层返回的函数才负责接收数据。理解这层关系后，再根据 `A`、`B`、`C` 检查每一步输入和输出是否能衔接起来。

容易出错的地方：

- `reduce` 忘记使用初始值。
- `zipWith` 没有按位置配对。
- `map` 返回的不是新列表，而是修改原列表导致副作用。

### 5. Task 0.4：Module 和 Parameter

需要写代码的文件：`Human/0_torch_basics/minitorch/module.py`。

你要完成 `Module` 对参数和子模块的递归管理。具体工作包括：

- `train()`：把当前模块和所有子模块切到训练模式。
- `eval()`：把当前模块和所有子模块切到评估模式。
- `parameters()`：收集当前模块和所有后代模块中的 `Parameter`。
- `named_parameters()`：收集参数时保留层级路径，避免重名参数混在一起。

#### 知识点：模块树与参数注册

神经网络不是平铺的参数列表，而是由层嵌套成的树。`Module` 节点既可以直接拥有参数，也可以拥有子模块；参数注册让优化器能够从根节点递归发现所有可训练值，训练/评估模式则需要沿同一棵树传播。参数名中的层级前缀相当于从根模块走到该参数的路径。

#### 大概实现逻辑

把“当前节点”和“所有子节点”分开处理：先遍历本节点保存的参数，再递归访问每个子模块，并在命名版本中拼接子模块路径。模式切换同样先更新当前节点，再把相同操作传播到后代。实现时应依赖类中已有的注册容器与属性机制，保持遍历顺序稳定，同时避免把普通字段误收集为参数。

容易出错的地方：

- 只收集当前模块参数，忘记递归子模块。
- 子模块参数没有加前缀，导致名字冲突。
- `train()` 和 `eval()` 只改当前节点，不改子节点。
- 把普通属性误当参数，或者把参数没有放进 `_parameters`。

验证位置：`Human/0_torch_basics/tests/test_module.py` 中标记为 `task0_4` 的测试。

调试时可以用 `Human/0_torch_basics/project/module_interface.py` 的可视化理解模块树，但真正要改的核心文件仍然是 `minitorch/module.py`。

## 第三章：代码实现、逻辑与细节讲解

这一章解释当前代码如何实现上面的目标。现在可以进入实现细节，因为前两章已经建立了为什么要这样做。

### 1. 整体代码结构

本模块核心文件如下：

- `minitorch/operators.py`：基础数学函数和高阶函数。
- `tests/test_operators.py`：算子和性质测试。
- `minitorch/module.py`：`Module` 和 `Parameter`。
- `tests/test_module.py`：参数树和模式切换测试。
- `minitorch/datasets.py`：二维分类数据集。
- `project/run_manual.py`：手工线性分类器。
- `README.md`：训练或可视化交付记录。

这套结构的重点是：实现文件负责行为，测试文件负责定义正确性，README 负责记录结果。

### 2. `operators.py`：深度学习框架的最小数学语言

`operators.py` 中的函数分三类。

第一类是普通数值函数：

- `mul`
- `add`
- `neg`
- `id`
- `max`
- `lt`
- `eq`
- `inv`
- `log`
- `exp`

它们让后续 Scalar 和 Tensor 可以复用同一套数学定义。

第二类是神经网络常用非线性：

- `sigmoid`
- `relu`

没有非线性，多层神经网络本质上还是一个线性函数，表达能力会很弱。sigmoid 常用于把输出压到 0 到 1 之间，ReLU 常用于隐藏层。

第三类是局部反向函数：

- `log_back`
- `inv_back`
- `relu_back`

它们在 Module 0 中看起来有点超前，但后面自动微分会用到。它们表示：如果输出端传来一个梯度 `d`，这个函数应该把多少梯度传给输入端。

### 3. 高阶函数：把标量操作推广到列表

`map(fn)` 返回一个新函数，这个新函数会把 `fn` 应用到列表每个元素。

`zipWith(fn)` 返回一个新函数，这个新函数会同时遍历两个列表。

`reduce(fn, start)` 返回一个新函数，这个新函数会从 `start` 开始累积。

因此：

- `negList` 是把 `neg` 提升到列表上。
- `addLists` 是把 `add` 提升到两个列表上。
- `sum` 是用 `add` 折叠列表。
- `prod` 是用 `mul` 折叠列表。

这个思想在 Module 2 会再次出现：Tensor 的 `map`、`zip`、`reduce` 本质上也是同样想法，只是数据从 Python 列表变成了多维 storage。

### 4. `module.py`：参数树

`Module` 的关键设计是把参数和子模块分别存起来：

- `_parameters` 保存当前模块直接拥有的参数。
- `_modules` 保存当前模块直接拥有的子模块。

当执行：

```text
self.p = Parameter(...)
self.layer = Module(...)
```

`__setattr__` 会根据类型决定放到哪个字典里。

`named_parameters()` 的逻辑是：

1. 先收集当前模块自己的参数。
2. 再遍历每个子模块。
3. 对子模块返回的参数名加上 `子模块名.` 前缀。

这就是为什么测试能找到：

```text
a.p2
b.c.p3
```

`train()` 和 `eval()` 则是树上的递归操作。它们先改变当前模块状态，再对子模块调用同名方法。

### 5. `run_manual.py`：手工分类器

当前手工模型是：

```text
output = sigmoid(5.0 - 10.0 * x0)
```

当 `x0 = 0.5` 时，括号里正好是 0，sigmoid 输出 0.5。这就是分类边界。

当 `x0 < 0.5` 时输出大于 0.5；当 `x0 > 0.5` 时输出小于 0.5。因此它能匹配 Simple 数据集的竖直分割规则。

### 6. 测试在验证什么

`tests/test_operators.py` 主要验证：

- 基础函数是否和 Python 行为一致。
- sigmoid、lt、mul、add 是否满足数学性质。
- 高阶函数是否能正确处理列表。
- 反向局部函数是否至少能运行并满足简单行为。

`tests/test_module.py` 主要验证：

- 参数能否被访问。
- 嵌套模块参数名是否正确。
- `parameters()` 数量是否正确。
- `train()` 和 `eval()` 是否递归传播。
- `__call__` 是否转发到 `forward()`。

### 7. 常见 bug 和排查方式

如果基础算子测试失败，先用普通 Python 表达式对照，不要立刻怀疑测试。

如果 property test 失败，先看 Hypothesis 给出的最小反例。它通常比随机猜测更有价值。

## 第四章：Python 语言机制与抽象工具

这一章不再按 Task 顺序重复作业要求，而是按知识之间的关系进行整理：`typing`、函数作为参数、函数作为返回值共同解释 Task 0.3 的高阶函数；对象属性机制则解释 Task 0.4 的 `Module` 为什么能自动管理参数和子模块。

### 1. `typing` 的使用

类型标注的首要作用是描述契约：一个函数需要什么、会返回什么，以及多个位置上的类型应该保持怎样的关系。Python 通常不会在运行时根据这些标注自动阻止错误类型，因此类型标注不能代替实际逻辑和测试。

#### `operators.py` 中的类型组件

- `TypeVar("A")`：创建类型变量。`A` 不是某个固定类型，而是一个占位符，用来表达“出现在这些位置上的类型彼此相关”。`A`、`B`、`C` 使用不同字母，表示输入和输出可以是不同类型。
- `Callable[[A], B]`：描述一个可调用对象。它接收一个 `A`，返回一个 `B`。
- `Callable[[A, B], C]`：描述一个二元可调用对象。它依次接收 `A` 和 `B`，返回 `C`。
- `Iterable[A]`：表示能够逐个产生 `A` 类型元素的对象。它强调“可以遍历”，不要求输入一定是列表。
- `List[B]`：表示一个列表，并且其中每个元素都是 `B` 类型。与 `Iterable` 相比，它还明确了输出容器的形式。

读复杂类型时，可以先找最外层函数的输入和输出，再逐层展开。例如，一个高阶函数的返回类型仍然是 `Callable`，说明第一次调用结束后得到的不是最终计算结果，而是另一个可以继续调用的函数。

#### `module.py` 中的类型组件

- `Any`：表示这里暂时不限制值的具体类型。它适合框架边界，但也意味着类型检查器能提供的保护更少。
- `Dict[str, Module]`：表示键是字符串、值是 `Module` 的字典。`_modules` 正是用这种结构把子模块名字映射到子模块对象。
- `Sequence[Module]`：表示一段有顺序、可读取的 `Module` 对象。它比 `List[Module]` 更关注“返回有序集合”这一能力，而不是限定具体容器。
- `Tuple[str, Parameter]`：表示一个固定的二元组，第一个位置是参数名，第二个位置是 `Parameter` 对象。
- `Optional[str]`：表示值可以是 `str`，也可以是 `None`。

文件开头的 `from __future__ import annotations` 会推迟类型标注的求值。这样，类体内部写到 `Module` 或尚未在运行时完成定义的类型时，不必立刻把它解析成具体对象，尤其适合类引用自身的场景。

### 2. 函数作为参数传入

Python 中的函数也是对象，因此可以像数字、字符串和列表一样，赋给变量或传给另一个函数。把函数作为参数传入，本质上是在传递一种“行为”。

普通参数通常回答“要处理什么数据”，函数参数则回答“遇到数据时要做什么”。例如，高阶函数负责遍历列表，但它并不知道每个元素应该取负、相加还是做其他变换；调用者传入的函数补上了这部分规则。

这种拆分有三个作用：

1. 遍历逻辑只写一次，不需要为每种运算重复组织列表。
2. 高阶函数不依赖某个具体数学操作，可以处理更多类型和行为。
3. 测试时可以分别验证“遍历是否正确”和“单步函数是否正确”。

理解函数参数时，可以问三个问题：这个函数需要几个参数？每个参数来自哪里？它的返回值会被保存、继续累积，还是直接丢弃？这些问题分别对应 `map`、`zipWith` 和 `reduce` 的不同数据流。

### 3. 函数作为输出

函数不仅可以作为输入，也可以作为另一个函数的返回值。此时，第一次调用是在配置规则，返回的新函数才会在第二次调用时处理实际数据。

返回的内部函数还能记住创建它时所在作用域中的变量，这种机制称为闭包。例如，一个列表处理函数可以记住先前传入的单步函数；累积函数还可以同时记住初始值。即使外层函数已经调用结束，这些被内部函数使用的变量仍然可以在之后访问。

可以把过程理解为：

```text
高阶函数 + 计算规则 -> 已配置的列表函数
已配置的列表函数 + 实际数据 -> 最终结果
```

这不是为了把简单调用写复杂，而是为了把“固定的策略”和“不断变化的数据”分开。阅读这类代码时，先确认当前拿到的是最终值还是一个待调用的函数，再查看内部函数捕获了哪些外层变量。

### 4. `__dict__` 与 Python 属性访问

普通 Python 实例通常使用 `__dict__` 保存自己的实例属性。它是一个从属性名到属性值的字典。例如，给对象设置 `name` 和 `count` 后，其内部状态可以概念化为：

```text
{"name": 某个值, "count": 某个值}
```

不过，并非所有 Python 对象都有 `__dict__`；使用 `__slots__` 的类和部分内置类型可能采用其他存储方式。

#### 普通属性访问和直接字典访问

`obj.attr` 使用 Python 的完整属性访问机制。读取时会检查实例属性、类属性和描述符；如果常规查找失败，才可能调用类定义的 `__getattr__`。写入时则会经过 `__setattr__`，类可以在这里检查、转换或重新存放传入的值。

`obj.__dict__["attr"]` 直接读取实例底层字典中的键，不负责类属性查找，也不使用 `__getattr__` 提供的回退结果。如果键不存在，它会产生 `KeyError`。同样，直接修改 `obj.__dict__` 会绕过自定义 `__setattr__` 的处理。

因此，两种写法在简单对象上可能得到同一个值，但语义并不完全相同：

- `obj.attr` 表示“按照这个类规定的属性规则访问 `attr`”。
- `obj.__dict__["attr"]` 表示“直接访问实例自身保存的原始数据”。

#### 为什么框架代码会直接使用 `__dict__`

框架经常重写 `__setattr__` 和 `__getattr__`，将某些属性登记到专用容器中，同时仍允许使用普通属性语法访问它们。在实现这些属性钩子时，直接读取 `__dict__` 可以明确访问的是底层容器，避免再次进入自定义属性转发逻辑而产生递归。

在当前 `Module` 中，`_modules` 是直接保存在实例 `__dict__` 里的子模块注册表，而具体子模块保存在这个注册表内部。因此：

```text
self.__dict__["_modules"] -> 子模块注册表
子模块注册表[名称]        -> 具体子模块
```

在初始化完成后，`self._modules` 通常也能取得同一个注册表；直接写 `self.__dict__["_modules"]` 的重点是明确访问层级，而不是为了单纯提高性能。

一般业务代码应优先使用正常属性语法。只有在实现属性管理、序列化、调试工具或底层框架机制，并且确实需要绕过自定义属性行为时，才适合直接操作 `__dict__`。
